# 構文の書き換え対照表

AI が生成した日本語に出やすい構文と、その書き換え例をまとめる。
SKILL.md の「改稿の手続き」にある「文単位の書き換え」で、書き方に迷ったときに参照する。
書き換え後の例は、原文の前後から主体や内容を特定できる場合の書き方である。
特定できない主体、数値、原因、効果は補わず、書き手に確認する。

この対照表は、[yomiyasu](https://github.com/nanaism/yomiyasu) の `references/gemini-syntax.md` と `references/domains/` を、この規範の表記と規則に合わせて書き直したものである。

## 動作主、対象、動作を一文の中で確定させる

主語の省略、受動態、指示語（「これ」「両者」「片方」）が重なると、一文だけでは意味が確定しない。
処理や判断をする主体を主語に置き、指示語は指す名詞に戻し、動詞は何がどう変わるのかを直接書く。

| 書き換え前 | 書き換え後 | 直した点 |
|---|---|---|
| 片方だけを見て基準を作ると、もう片方が壊れます。 | 開発速度だけを基準にすると、保守性の要件を満たせなくなるおそれがあります。 | 「片方」と「壊れる」を具体化した |
| 依存構造は分割できない。動かしながら引き返す。 | 依存関係を分離できないため、稼働中のシステムを変更し、問題が発生した場合は元の状態に戻します。 | 主語、条件、対象を明記した |
| 前提を、経路が代わりに添える。 | 運用者は問い合わせ先に応じた前提条件を参照します。 | 「経路」という無生物主語を、運用者の行為に戻した |
| 読んで身に付けてから、効く。効いてから、身に付く。 | 実際の業務で使い、効果を確かめながら使い方を習得します。 | 抽象的な連鎖を、具体的な学習の手順にした |

## 読者への要請とシステムの機能を書き分ける

「〜します」とだけ書くと、書き手と読者とシステムのどれが行うのかが曖昧になる。

| 書き換え前 | 書き換え後 |
|---|---|
| 環境に読み込ませて使用します。 | 環境に読み込ませて使用してください。 |
| 引数を渡して実行します。 | 引数を渡して実行できます。 |

## 擬人化を解く

概念、道具、アーキテクチャ、出来事が、意思や感情を持って行動しているかのような書き方を、人や組織の行為か、観測できる事実に戻す。
論文で慣用される「結果は〜を示す」は残してよい。

| 書き換え前 | 書き換え後 |
|---|---|
| この事例が残したのは、先例である。 | この事例は、先例として参照できます。 |
| アーキテクチャが開発者に規律を要求する。 | 開発者はアーキテクチャの規則に従ってコードを書きます。 |
| 文化が醸成され、プロセスが定着していく。 | チーム内で自主的にレビューする習慣が定着しました。 |
| 街中の散歩が、都市の動線と建築の対話を浮かび上がらせる。 | 街を歩いていると、道路や建物の配置がよく考えられていると感じます。 |

## 比喩動詞を操作や状態変化に戻す

| 書き換え前 | 書き換え後 |
|---|---|
| 判断に迷うものは、残さない側に倒します。 | 採否を判断できない項目は、原則として除外します。 |
| この設定が地味に効いてきます。 | この設定をしておくと、予期しない動作不良を防げます。 |
| キャッシュが切れた瞬間に静かに壊れる。 | キャッシュが無効化された場合、警告やエラーを出力せずに処理が失敗するおそれがあります。 |
| パイプラインが黙ってスキップする。 | パイプラインは警告を出さずに処理を終了します。 |
| デバッグに丸一日溶かした。 | 原因の特定と動作の検証に丸一日かかりました。 |
| この関数が整合性を担保する。 | この関数を実行すると、データの整合性を維持できます。 |

## 前置きと否定対比を肯定文にする

前置きを削って要点から書き始め、誤解を解く必要がない否定対比は肯定文で書く。

| 書き換え前 | 書き換え後 |
|---|---|
| 知りたいのは、価格ではなく判断軸です。 | どのような判断基準で最終価格を決定したのか教えてください。 |
| 正解ラベルだけで測ってはいない。 | 評価には正解ラベルだけでなく人間の選好率も併用しました。 |

## ダッシュを助詞でつなぐ

| 書き換え前 | 書き換え後 |
|---|---|
| 重要な機能――とりわけ認証周り――は慎重に実装する必要があります。 | 認証機能をはじめとする重要な処理は、慎重に実装する必要があります。 |

## 情報を増やさない補足括弧を削る

| 書き換え前 | 書き換え後 |
|---|---|
| 修正前のAI生成文（素の出力） | 修正前のAI生成文 |
| 不自然な日本語（いわゆるAI臭さ） | AI特有の不自然な日本語 |

## 和文と英数字のあいだの空白を除く

新規の文書で、既存原稿の流儀や投稿先の指定がない場合に当てる。

| 書き換え前 | 書き換え後 |
|---|---|
| この README は、 yomiyasu で 生成させた文章です。 | このREADMEは、yomiyasuで生成させた文章です。 |

## 業務文書の例

業務文書では比喩を使わず、条件と主体を直接書く。

| 書き換え前 | 書き換え後 |
|---|---|
| 判断に迷うものは、残さない側に倒す。 | 採否基準を満たさないレコードは、登録対象から除外する。 |
| ここを読み違えると前提が崩れやすい。 | この前提条件を満たさない場合、後続の処理でエラーが発生するおそれがあります。 |
| 操作の手触り感を確認する。 | プロトタイプを操作し、主要機能の操作性をテストする。 |
| 議論の解像度を上げる。 | 検討項目のコスト試算と対応期日を具体化する。 |
| コストをモデル規模へ配る。 | 固定計算量をパラメータ数とトークン数に配分する。 |

## エッセイの例

エッセイでは、体験を教訓に仕立てず、書き手の実感をそのまま書く。

| 書き換え前 | 書き換え後 |
|---|---|
| カフェのコーヒーが哲学を凝縮している。日常の喧騒という虚飾を剥ぎ取った先に現れる静謐な真実。 | ここのマスターはコーヒーの豆選びにすごくこだわっていて、酸味が少なくて飲みやすかった。 |
| スペックという虚飾を剥ぎ取った時、指先が感知した真実とは。 | 3年使いましたが、REALFORCEは打鍵感が柔らかすぎると感じ、私はHHKBのほうが好みでした。 |
